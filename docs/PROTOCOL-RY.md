# RongYuan RY5088 protocol notes

FCC's notes on the protocol of Hall-effect boards built on RongYuan's RY5088 firmware: MonsGeek FUN60 / FUN68 /
M1 V5 HE, many Akko boards and others that MonsGeek's web driver (app.monsgeek.com) configures. The driver is
`app/src/hid/ry.ts`; the model list is generated by `tools/catalog/build-ry.js` from the web driver's own data.

This protocol is unrelated to the Sonix one in [PROTOCOL.md](PROTOCOL.md).

## Transport

| | |
|---|---|
| Interface | vendor collection, usage page `0xFFFF`, usage `0x02` (USB interface 2) |
| Reports | feature report id `0`, 64 bytes, both directions |
| Vendor ids | `0x3151` (MonsGeek / Akko) and others in the catalogue, e.g. `0x38EE` (FUN60 Ultra TMR) |

A command is sent with SET_FEATURE; its answer is read with GET_FEATURE. The official app waits about 10 ms before
each send and each read, and about 100 ms after writes that the keyboard saves.

```
byte 0     command
bytes 1-6  parameters
byte 7     checksum: 255 - (sum of bytes 0..6 & 0xFF)          ("bit7")
bytes 8-63 data
```

Lighting (`0x07`) puts the checksum at byte 8 instead: `255 - (sum of bytes 0..7 & 0xFF)` ("bit8").

GET commands echo the command byte in byte 0 of the answer. Paged reads (key matrix, macros, per-key tables, user
picture) answer with a bare 64-byte page and no echo.

## Identification

`0x8F` returns `[0x8F, model id (u32 LE), …, firmware (u16 LE at bytes 7-8)]`. The USB product id is shared by many
models, so FCC picks the model by this id (the same way the official app does).

`0xE6` (feature list) answers `[0xE6, 0xAA, precision, …]` on newer firmware. Precision: 0 = 0.01 mm, 1 = 0.005 mm,
2 = 0.001 mm. Without a feature list the firmware version decides: below 768 = 0.1 mm, below 1280 = 0.01 mm, else
0.005 mm. **FCC only writes travel values after checking that every key's stored actuation makes sense in those
units**; otherwise actuation and DKS editing stay off and the user is asked for a board report.

## Commands FCC uses

| Cmd | Name | Notes |
|---|---|---|
| `0x83` / `0x03` | polling rate | byte 2: 0 = 8000 Hz, 1 = 4000, 2 = 2000, 3 = 1000, 4 = 500, 5 = 250, 6 = 125 |
| `0x84` | active profile | byte 1 (0-3); FCC edits the profile that's active when it connects |
| `0x86` / `0x06` | debounce | byte 1, ms |
| `0x87` / `0x07` | lighting | `[mode, MAXSPEED - speed, brightness 0-4, option, r, g, b]`, bit8 checksum |
| `0x89` / `0x09` | keyboard options | `[os, fn layer, anti-mistouch, RT stability 0-5 (x25 ms), WASD swap]` |
| `0x8A` / `0x0A` | key matrix | see below |
| `0x8B` / `0x0B` | macros | see below |
| `0x8C` / `0x0C` | user picture | per-key colours, see below |
| `0x91` / `0x11` | sleep timers | u16 LE seconds at bytes 8-15 (wireless boards) |
| `0xE5` / `0x65` | per-key tables | see below |
| `0x01` | factory reset | Danger zone only |

Everything else is refused by the driver before it reaches the keyboard, including the bootloader (`0x7F`), flash
erase (`0xAC`), SKU (`0x50`), screen and firmware-update commands.

### Lighting option byte

`option = variant << 4 | colour mode`. The colour-mode values for rainbow ("dazzle") and single colour, the top speed
and the mode list differ between model classes (e.g. 8/7 on some, 7/8 or 7/1 on others), so the catalogue carries them
per model. Mode 13 (user picture) uses `option = slot << 4` and colour `0, 200, 200`. The official app sends white as
`#FAFAFA`.

### Key matrix

Keys are numbered by matrix position, column-major with 6 rows per column. Each position holds 4 bytes, on 4
sub-layers per profile.

- Read one sub-layer: `[0x8A, profile, 0xFF, page 0-7, sub-layer]`: 8 pages of 64 bytes (128 positions).
- Write one key: `[0x0A, profile, position, 0, 0, 1, sub-layer, checksum, b0, b1, b2, b3]`.
- Write a whole sub-layer: `[0x0A, profile, 0xFF, page, length, last, sub-layer, checksum, 56 bytes]`, 10 pages.

| Entry | Meaning |
|---|---|
| `[0, mods, key, 0]` | key with modifiers (`[0,0,0,0]` = nothing: there's no fallback to the factory key) |
| `[3, 0, usage lo, usage hi]` | consumer (media) key |
| `[1, 0, 240-244, 0]` | mouse left, right, middle, back, forward |
| `[1, 0, 245, 1 / 255]` | wheel up / down |
| `[9, type, macro, 0]` | macro: type 0 = repeat count (stored in the macro), 1 = toggle, 2 = while held |
| `[10, 1, 0, 0]` | Fn |

Sub-layers 1-3 matter for advanced keys: mod-tap keeps its hold key on sub-layer 0 and tap key on 1; DKS uses all four
as its four bindings. A key that leaves an advanced mode gets its own key back on sub-layer 0 and `[0,0,0,0]` on 1-3.

### Per-key tables (`0xE5` read, `0x65` write)

- Read: `[0xE5, table, 1, page]`, pages of 64 bytes.
- Write a whole table: `[0x65, table, 1, page, commit, …, 56 bytes]`.
- Write one key: `[0x65, table, 0, position, commit, …, value]`.
- `commit` is set on the last packet of a batch; the keyboard then saves (give it ~300 ms before reading again).

| Table | Content | Size |
|---|---|---|
| 0 | actuation travel | u16 per key |
| 1 | release travel (FCC keeps it equal to actuation) | u16 |
| 2 / 3 | rapid trigger press / release sensitivity | u16 |
| 4 | DKS trigger point (first and last stage) | u16 |
| 5 | mod-tap time, 10 ms steps | u8 |
| 7 | key mode: 0 normal, 2 DKS, 3 mod-tap, 4 toggle, 5 rapid-fire toggle, 7 snap tap; `0x80` = rapid trigger on | u8 |
| 8 | DKS bindings, write only, per key: 4 bytes, one per binding, 2 bits per stage (0 none, 1 tap, 2 hold to next stage, 3 hold across) | |
| 9 | snap tap partner position (`0xFF` = none) | u8 |
| 10 | DKS bindings, read: 4 blocks of 128 bytes (one per binding) | |
| 254 | live key travel | u16 |

Travel values are in the precision units above. DKS has one trigger point for its first and last stage (table 4)
and uses the key's actuation travel (table 0) for the two deeper stages.

### Macros

Read: `[0x8B, slot, page 0-3]`. Write: `[0x0B, slot, page, 56, last, …, 56 bytes]`. Up to 256 bytes per macro:

```
u16 repeat count, then events:
  [code, down<<7 | delay]                 delay 1-127 ms
  [code, down<<7, delay lo, delay hi]     longer delays
  code 4-239 = HID key, 240-244 = mouse buttons; 0xF9 = mouse move
ends with 4 zero bytes
```

A zero delay is never sent: it would make the firmware read the next event as a delay.

### User picture (per-key colours)

Read: `[0x8C, slot, 0xFF, page 0-5]`. Write: `[0x0C, slot, 0xFF, page 0-6, length (56, last 42), last, …]`. RGB for
126 matrix positions, in position order. FCC uses slot 0.

## Not supported (yet)

2.4 GHz dongles and Bluetooth (the dongle relays commands with its own polling), the Fn layer, side lighting, screens,
music / screen-sync lighting, gamepad mode.
