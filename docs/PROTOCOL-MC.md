# MCHOSE protocol notes (first generation)

FCC's notes on the protocol of MCHOSE's magnetic keyboards that use their first-generation ("glw") firmware: ACE 60 /
60 Pro / 60X, ACE 68 / 68 Air / 68 GT / 68 Turbo, ACE 75, JET 75, ZERO 75X, MIX 87, K87S, K99 V3 and G75 V2. Worked
out from MCHOSE's web driver (www.mchose.com.cn); the driver is `app/src/hid/mc.ts` and the model list is generated by
`tools/catalog/build-mc.js`. MCHOSE's newer boards (G98 V3 and similar) use a different protocol FCC doesn't speak.

## Transport

| | |
|---|---|
| Interface | generic-desktop collection, usage page `0x0001`, usage `0x0000` |
| Out | output report 0, 64 bytes |
| In | input report, 64 bytes |
| USB ids | e.g. ACE 60 `41E4:2101` (also `19F5:FC30`) |

```
request  [0x55, cmd, 0, checksum, length, offset lo, offset hi, 0, data…]
reply    [0xAA, cmd, …, length, offset lo, offset hi, …, data from byte 8]
checksum = sum(length, offset lo, offset hi, 0, data…) & 0xFF
```

A reply belongs to a request when its command, offset and length (≤ the requested one) match; the board also sends
unsolicited reports (profile changes, battery …) which are skipped. Every command, reads and writes alike, works on a
memory area at an offset, at most 56 bytes per message.

## Areas FCC uses

| Read | Write | Area | Offset per profile | Layout |
|---|---|---|---|---|
| 3 | | info | | firmware at bytes 0-1 (hex, e.g. `0x0120` = v1.20) |
| 4 | | base | | `[order index, profile count, order…]`; active profile = `order[byte 0]` |
| 5 | 6 | function config | 64 | settings + lighting, below |
| 7 | | factory key map | 512 × (4 × profile + layer) | 3 bytes per key |
| 8 | 9 | key map | 512 × (4 × profile + layer) | 3 bytes per key |
| 10 | 11 | per-key colours | 512 | RGB per key |
| 12 | 13 | macros | 4096 shared (ACE 60) | below |
| 160 | 161 | key triggers | 1024 | 8 bytes per key |
| 164 | 165 | mod-tap slots | 256 | 6 bytes × 32 |
| 166 | 167 | toggle slots | 128 | 3 bytes × 32 |
| | 238 | factory reset | | `[255]` |

FCC refuses every other command, including boot mode, ROM erase / write and firmware update.

### Keys (3 bytes: type, code1, code2)

| Type | Meaning |
|---|---|
| 16 | keyboard: `code1` = modifier bits, `code2` = HID usage |
| 32 | mouse button: `code1` = mask (1 left, 2 right, 4 middle, 8 back, 16 forward) |
| 33 | wheel: `[33, 0, 1 / 255]` |
| 48 | consumer key: usage in `code1` (low) and `code2` (high) |
| 112 | macro: `[112, index, mode]` |
| 144 / 145 / 146 / 148 | DKS / toggle / mod-tap / SOCD: `code1` = slot (mod-tap: `code2` = time ÷ 10 ms) |
| 240 | lighting and Fn functions (`[240, 255, n]` = Fn) |
| 255 | unset |

### Key triggers (8 bytes per key)

```
0  0xA0 | switch type
1  priority << 4 | key mode (0 normal, 1 rapid trigger)
2  actuation - 1 (low 8 bits)         3  bit 0: actuation bit 8, bits 3-4 press precision, bits 1-2 release precision
4  RT press - 1 (low 8 bits)          5  bit 0: bit 8, bits 1-7 press dead zone
6  RT release - 1 (low 8 bits)        7  bit 0: bit 8, bits 1-7 release dead zone
```

Actuation is in the board's travel step (ACE 60: 50 per mm, others 100 per mm). Rapid trigger uses the precision
bits: 0 = the board's own step, 1 = 0.005 mm, 2 = 0.001 mm. FCC checks that every key's actuation makes sense in those
units before it writes any.

### Function config (64 bytes)

| Byte | |
|---|---|
| 1 | low 4 bits: OS mode |
| 4 | low 4 bits: polling rate code, high 4 bits: tick rate |
| 6 | bit 0 Win lock, bit 1 Alt-Tab lock, bit 2 Alt-F4 lock |
| 7 | bit 0 berserk ("tachyon"), bit 1 bottom rapid trigger, bit 2 travel check, bit 3 debug, bits 5-7 debounce level |
| 8-16 | lighting: effect, brightness 0-100, 4 − speed (0-4), direction, rainbow, colour index, R, G, B |
| 35 | sleep time in 30 s steps |

Lighting effects: 0 custom (per-key colours), 1 rainbow cycle, 2 gradient, 3 static, 4 breathing, 5 disco, 6/7
horizontal / vertical wave, 8 centre spread, 9 starlight, 10 spiral, 11 rise and fall, 12 bounce, 13 reactive ripple,
14 ripple, 15 afterimage, 16 reactive fireworks, 17 light pillars, 18 diagonal flow, 19 laser rain, 20 twinkle,
21 fireworks, 22 triangle bounce; 255 off where the board lists it.

### Macros

```
bytes 0-31   16 × u16 offset of each macro's records
bytes 32-33  0x81, 0x7E
bytes 34-49  play type per macro
from 64      records, 4 bytes each: [delay lo, delay hi, flags, code]
             flags: bit 7 last record, bit 6 down, low 6 bits: 1 modifier (code = bit), 2 key, 3 mouse
             an empty macro points at a shared [0, 0, 0x80, 0]
```

Delays under 5 ms are stored as 4 ms, as the official app does.

## Not supported yet

DKS (the stage-action bits aren't confirmed), SOCD (its group byte), macro play modes other than "once", polling rate
(the code table), live key travel (the debug stream format) and the wireless dongles. All of these are left untouched
on the keyboard.
